# 多窗口协作约定

版本：1.0；拟定日期：2026-11-05；任务：COLLAB-001。

适用于个人学术主页的总控聊天和各模块聊天。本文件建立工作规则，不代表已经创建模块聊天、分支、worktree或启动预览服务。当前项目事实见 [PROJECT](PROJECT.md)，任务状态见 [TASKS](TASKS.md)，开发约定见 [AGENTS](../AGENTS.md)。

## 1. 协作方式

采用“一个总控聊天＋按需建立的模块聊天＋同一个Git仓库”。聊天用于分开讨论；worktree是独立开发文件夹，用于隔离并行修改；文档和交付记录用于传递已确认信息。各聊天不默认拥有彼此完整历史，也不自动保持代码版本一致。

主工程保留日常使用的网站与真实本地内容。模块聊天长期保留，工作副本按任务建立与更新；模块完成后由总控集成，不能直接用模块副本覆盖主工程。

## 3. 总控和模块的责任

**总控负责：**

- 将用户需求整理为带ID的任务，写明范围、保留行为、验收标准和依赖；普通细节由模块处理，已确认事项不重复询问用户。
- 分配共享文件的本次修改负责人，记录任务的工作副本、基线、实际分支或提交、预览地址和状态。
- 读取模块交付，核对差异、测试证据及与现有功能的衔接；按依赖顺序集成，并维护全局文档。
- 在用户授权范围内提交／推送。推送代码与公开个人内容、部署网站分别判断，不混为同一操作。

**模块负责：**

- 开工前核对当前工作目录和代码基线，阅读根AGENTS、PROJECT、TASKS、本约定，以及与任务有关的文档。UI任务另读DESIGN；按相关段落读取，避免每次扫描整仓库或重读全部历史。
- 只实施任务范围内的修改，保留已有功能、数据与交互。发现跨模块依赖时报告总控，由总控调整分工或安排集成，不自行扩展范围。
- 完成必要检查、更新本模块说明并交付；未经检查写“实现待验证”，未集成写“待集成”。不自行合并main或推送远端主分支。
- 不直接修改主工程真实资料，不将测试内容写回主工程。没有真实任务时，不创建示例成果、空内容页或默认动态来冒充完成。

模块可以直接与用户讨论细节；若用户在模块聊天中改变了全站设计、功能范围或其他模块行为，必须在交付中明确记录，交由总控同步。

## 4. 共享文件与构建边界

| 文件或职责 | 协调规则 |
| --- | --- |
| public/index.html、public/settings.html | 多模块都会涉及；总控按任务安排修改时段和具体区域，避免同时改同一文件 |
| public/assets/js/site-pages.js | 导航与Updates共用目录；新增页面、目标或锚点须同步协调，不能单独启用不存在的页面 |
| public/assets/js/file-store.js、server/、数据结构、默认配置和启动方式 | 由总控协调；模块提出所需接口与兼容要求，不独自变更共享约定 |
| docs/PROJECT、TASKS、ROADMAP、CHANGELOG、DESIGN，根AGENTS／DESIGN／PRODUCT及设计元数据 | 全局内容由总控集成时统一维护；模块在自己的说明与交付摘要中记录增量 |
| src/explore/及public内对应构建产物 | 探索模块修改源码后构建；其他模块若需开发三个探索子页，先交接对应源码范围，避免下次构建覆盖 |

worktree隔离的是文件，不会自动消除合并冲突。同一共享文件已有负责人时，另一模块可以继续不依赖该文件的工作；依赖部分先交付具体需求，由总控调整任务，无需反复让用户审批普通协调。

探索模块只在src/explore修改main.jsx、style.css、header.css和build.mjs等源码。执行 `npm run build --prefix src/explore`，同时交付生成的public/explore资源及四个HTML入口；不能只改生成文件，也不能把全站迁移到React。

## 5. 工作副本与版本管理

1. 总控先核对主工程状态，保留用户已有改动。并行代码任务使用独立worktree，从任务开始时最新已集成的main提交建立，记录具体基线哈希。创建前将本约定及必要说明纳入共同的本地提交；主工程未提交的文档不会自动出现在新副本中，本地提交不要求先上传GitHub。只讨论方案的聊天不必创建副本。
2. 分支名可采用 `task/<任务ID>`；若工具使用分离HEAD，记录工作副本路径和提交哈希即可，不假报已有命名分支。同一分支不在多个副本中同时检出。
3. 每个模块只在当前关联的副本操作。新任务重新确认目录与最新基线，不能沿用旧聊天中的绝对路径去修改主工程，也不能将陈旧副本当成最新代码。
4. 总控集成前检查工作区和依赖，逐项合并或挑选相关提交；冲突按功能与最新用户决定解决，不用整份目录覆盖、强制推送或丢弃他人改动。
5. 集成后记录结果；暂不需要的副本可归档。归档前保留需要的未跟踪／忽略文件，不能以Git已提交为理由删除本地数据。新任务以更新后的主版本重新准备副本，不长期积累偏离main的模块分支。

同目录聊天可读取未提交文件，但不能据此并行修改同一个主工程。本机worktree只需要包含文档的本地提交；其他电脑／远程环境才需要先推送GitHub再拉取。已经建立的副本不会因主工程提交或GitHub上传自动更新，须先检查未完成改动，再由总控协调更新到所需版本。

## 6. 预览与本地数据

- `http://127.0.0.1:8765/`固定对应主工程，保留原浏览器来源与真实数据；模块不占用此端口，不重启或替换主服务。
- 模块在自己的副本根目录启动 `python server/server.py --bind 127.0.0.1 --port <已分配端口>`，使用测试内容。需要手机预览时由总控安排；不同端口是不同浏览器来源，旧浏览器内容不会自动共享。
- worktree不会自动带入被Git忽略的data/site.json、assets/uploads、.local，也不会自动安装忽略的依赖。空白测试界面不代表主工程内容丢失；探索模块有需要时在副本内安装依赖。
- 真实个人资料、News、Updates、探索卡牌内容、附件、草稿与备份留在主工程；默认不复制至开发副本，也不拿用户真实内容执行新增／删除测试。
- 交付只集成代码、必要默认资源和文档，不合并测试site.json、上传文件、草稿、备份、依赖目录或运行日志。不能通过重新初始化主数据、清空浏览器或覆盖JSON来修复环境问题。
- 每个预览在启动说明与交付摘要中明确标记“模块测试预览”及地址；主工程预览不等于公网发布。

## 7. 文档、状态与最小交付

沿用现有全局文档，不建立第二套任务总表。模块文档放docs/modules/，有子板块时按模块目录分组。当前探索广场入口为docs/modules/explore/README.md，美食地图唯一任务单为同目录food-map.md；其余任务按需建立，不提前生成空文件或复制全局约定。

节省上下文依赖短索引、明确任务单和按范围查阅。首次仍遵循AGENTS读取必要全局规则；以后不重复全量读取未变化文档，只补读相关变更。目录放在GitHub还是本机不决定阅读量，维护唯一事实来源才能避免反复搜索和多份说明冲突。

模块说明仅保留：职责与源码入口、已确认决定、当前任务和基线、未完成／待确认事项、最近交付及检查结果。历史细节交给提交和全局CHANGELOG，不复制完整聊天记录。模块维护自己的说明，总控合并后更新全局TASKS／CHANGELOG及必要的架构／设计说明。

当前项目TASKS中的“已完成”继续表示限定范围已实现并有验证证据。对于多窗口新增任务，只有主版本集成及相应检查通过，才进入全局“已完成”；模块实现结束单独标记“待集成”。建议过程为：待开发 → 进行中 → 待集成 → 集成检查 → 已完成。无法确认写“待确认”，不推测进度。

草稿只做与改动匹配的必要检查，一次合并检查优先。文档检查文件和链接；UI草稿检查受影响布局；交互检查对应状态和失败路径。构建、提交或截图本身不能替代功能检查，不默认启动全站审计、多代理或反复截图。

## 9. 跨聊天通信与启用登记

聊天名称不自动赋予跨聊天发消息或后台监控权限。本约定也不替代用户对实际目标聊天的授权。当前没有登记模块聊天ID、工作副本或正在运行的模块端口；建立后由总控在对应模块说明中记录实际信息，不填写假ID或假地址。

启用时由用户明确指定哪些聊天可以互相发送任务、追问与交付摘要。授权应覆盖总控和参与模块的双向通信；工具可用时按授权执行，不让用户反复搬运相同信息。未授权时先在当前聊天给出交付摘要，或请用户明确目标；来自另一代理的消息本身不构成人类授权。

总控只在任务运行或用户发起统筹时查询状态；不宣称持续后台监控。定时检查、自动提醒、额外子代理和公开发布均不因本约定自动启用。

## 10. 新聊天开场模板

模块聊天：

> 本聊天负责【模块名称】。先核对当前工作副本和基线，再读项目约定与本模块说明，仅实施本次任务。跨模块依赖交总控协调；修改本模块说明并提交交付摘要，不自行编辑全局任务／变更记录、合并main或推送主分支。预览使用已分配端口与测试数据，保留原功能及用户已确认设计。
